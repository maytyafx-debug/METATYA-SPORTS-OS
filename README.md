# METATYA Sports OS

هسته ماژولار و چندسازمانی مدیریت باشگاه‌ها و سازمان‌های ورزشی. هسته مشترک مستقل از رشته ورزشی است و قابلیت‌های تخصصی هر رشته در ماژول‌های جداگانه توسعه می‌یابد.

## معماری پایه

- **Core Platform:** احراز هویت، کاربران، نقش‌ها، مجوزها و تنظیمات
- **Multi-Tenancy:** سازمان‌ها، باشگاه‌ها، عضویت‌ها و جداسازی داده هر سازمان
- **Sports Engine:** اعضا، مربیان، گروه‌ها، تمرین‌ها، رویدادها و نتایج
- **Business Engine:** امور مالی، شهریه، پرداخت، قرارداد و بیمه
- **Sport Modules:** قواعد و فرم‌های اختصاصی هر رشته، بدون وابسته‌کردن هسته به یک رشته
- **Portals:** پنل مدیر، مربی، ورزشکار و سرپرست
- **Intelligence:** گزارش‌ها، تحلیل عملکرد و مسیر رشد ورزشکار

## معماری ساده و جامع نسخه ۲

تجربه کاربری و نقشه محصول در شش بخش اصلی سازمان‌دهی می‌شود:

1. **مدیریت ورزش** — فدراسیون‌ها، هیئت‌ها، باشگاه‌ها، سازمان‌ها و نیروی انسانی
2. **افراد و توسعه** — ورزشکاران، مربیان، آموزش، استعدادیابی و مسیر رشد
3. **مسابقات و عملکرد** — تمرین، رویداد، رقابت، داوری، نتایج و عملکرد
4. **اقتصاد و امکانات** — مالی، قراردادها، بازار ورزش، تجهیزات و اماکن
5. **هوش و نوآوری** — تحلیل داده، هوش ورزشی، پژوهش، رسانه و تاریخچه
6. **زیرساخت و اعتماد** — هویت، دسترسی، امنیت، حریم خصوصی، ممیزی و بازیابی

سادگی شش‌بخشی به معنی حذف قابلیت‌ها نیست؛ قابلیت‌های تخصصی در زیرمجموعه‌ها و ماژول‌های مستقل قرار می‌گیرند. هر رشته ورزشی از هسته مشترک استفاده می‌کند و قوانین، داده‌ها، فرم‌ها و منطق تخصصی خودش را در ماژول نسخه‌بندی‌شده نگه می‌دارد.

## محدوده پیاده‌سازی فعلی

- پایه Next.js و Supabase SSR
- ورود و خروج کاربر
- عضویت چندسازمانی و انتخاب سازمان فعال
- کنترل دسترسی API با بررسی مجدد هویت و عضویت فعال
- جداول پایه سازمان، عضویت، عضو، رویداد و نتیجه
- سیاست‌های RLS در فایل Migration
- داشبورد اولیه برای ثبت و مشاهده اعضا، رویدادها و نتایج
- گردش CI برای TypeScript، ESLint و build

قابلیت‌های مالی، بیمه، تمرین، پرتال‌های اختصاصی، گزارش‌های پیشرفته و ماژول‌های رشته‌ای در نقشه راه هستند و هنوز نباید به‌عنوان قابلیت تکمیل‌شده تلقی شوند.

## راه‌اندازی محلی

1. فایل `.env.example` را به `.env.local` کپی کنید.
2. `NEXT_PUBLIC_SUPABASE_URL` و `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` را تنظیم کنید. اپلیکیشن فعلی از کلید عمومی Publishable استفاده می‌کند؛ متغیر قدیمی `NEXT_PUBLIC_SUPABASE_ANON_KEY` دیگر توسط کد runtime خوانده نمی‌شود.
3. وابستگی‌ها را نصب کنید: `npm install`
4. کنترل‌ها را اجرا کنید: `npm run typecheck`، `npm run lint` و `npm run build`
5. برای اجرای توسعه: `npm run dev`

هرگز کلید `service_role` یا کلید secret را در متغیرهای `NEXT_PUBLIC_*` قرار ندهید و فایل `.env.local` را commit نکنید.

## وضعیت دیتابیس و اجرای Migration

فایل `supabase/migrations/006_sports_multitenancy.sql` و Seed نمونه در مخزن آماده بررسی هستند؛ اما اجرای آن‌ها روی پروژه متصل، مرحله‌ای جداگانه و نیازمند تأیید مالک پروژه است.

پیش از اجرا باید:
- تاریخچه Migrationهای دیتابیس با فایل‌های مخزن تطبیق داده شود.
- وجود جداول و سیاست‌های هم‌نام بررسی شود.
- نسخه پشتیبان مناسب و امکان بازیابی بررسی شود.
- مقدار placeholder ایمیل در Seed با حساب Auth موجود جایگزین شود.
- SQL و اثر آن بر داده‌های موجود بازبینی شود.

تا پیش از تکمیل این بررسی و دریافت تأیید صریح، هیچ Migration یا Seed اجرا نکنید.

## امنیت Tenant

مرورگر شناسه سازمان انتخاب‌شده را در هدر `x-tenant-id` می‌فرستد. سرور این مقدار را به‌تنهایی معتبر نمی‌داند: در هر درخواست، کاربر را با `auth.getUser()` احراز می‌کند و عضویت فعال همان کاربر در همان سازمان را از دیتابیس بررسی می‌کند. سپس کوئری‌ها به شناسه سازمان تأییدشده محدود می‌شوند. RLS نیز لایه دفاعی مستقل است.

## استقرار آزمایشی روی Netlify

مخزن متصل به پروژه Netlify:

`https://github.com/maytyafx-debug/METATYA-SPORTS-OS`

شاخه انتشار: `main`  
Base directory: ریشه مخزن (خالی یا `/`)  
Build command: `npm run build`  
Publish directory: `.next`  
Node.js: نسخه 22

فایل `netlify.toml` در ریشه مخزن همین تنظیمات را ثبت می‌کند. Netlify نسخه سازگار Next.js Runtime را خودکار تشخیص می‌دهد و نیازی به نصب دستی `@netlify/plugin-nextjs` نیست. برای App Router، SSR و API Routes هیچ rewrite عمومی `/* → /index.html` اضافه نکنید.

### Environment Variables در Netlify

در **Project configuration → Environment variables** دو متغیر زیر را ثبت کنید:

| نام | مقدار |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | آدرس پروژه Supabase |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | کلید عمومی Publishable همان پروژه |

هر دو متغیر باید برای **Production** و **Deploy Previews** موجود باشند و Scope آن‌ها دست‌کم شامل **Builds** و **Functions** باشد (All scopes نیز مناسب است). چون پیشوند `NEXT_PUBLIC_` دارند، مقدارشان در bundle مرورگر قرار می‌گیرد؛ گزینه **Contains secret values** را برایشان فعال نکنید. هرگز `service_role`، Secret API Key، رمز دیتابیس یا JWT secret را در متغیرهای عمومی وارد نکنید.

**پاک‌سازی متغیر قدیمی:** در Netlify متغیر `NEXT_PUBLIC_SUPABASE_ANON_KEY` فعلی به‌عنوان Secret علامت خورده است. کد جدید دیگر آن را نمی‌خواند. پس از افزودن و تأیید `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`، متغیر قدیمی را از Netlify حذف کنید تا یک کلید عمومیِ bundleشونده به‌اشتباه در مخزن Secrets نگهداری نشود.

### مراحل بعد از Deploy

1. Build Logs را بررسی کنید و موفقیت مراحل Next.js build و Netlify Runtime را تأیید کنید.
2. دامنه نهایی Netlify را در Supabase → Authentication → URL Configuration به‌عنوان Site URL ثبت کنید.
3. مسیر `https://YOUR-NETLIFY-DOMAIN/auth/callback` را به Redirect URLs مجاز اضافه کنید.
4. ورود با حساب مجاز، Refresh، انتخاب سازمان فعال و APIهای عملیاتی را با داده آزمایشی بررسی کنید.
5. دسترسی سایت را در حالت Team SSO/private نگه دارید. انتشار عمومی و استفاده از داده واقعی ورزشکاران تا تکمیل آزمون‌های امنیتی مجاز نیست.

این استقرار فقط کد برنامه را Build می‌کند؛ هیچ migration یا SQL روی Supabase اجرا نمی‌شود. Migrationها و Seedها خارج از چرخه Deploy هستند و در این مرحله نباید اجرا شوند.
